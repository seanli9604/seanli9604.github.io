This is a brief walkthrough of the problem of peak deconvolution in chromatography-mass spectrometry, from the point of view of data processing. Anecdotally, I've found that chemists tend to not be completely familiar with what the software is doing underneath the hood for this specific problem. So, I wrote this to try to illustrate the conceptual principles underlying peak deconvolution.

Data from GC-MS or LC-MS is usually represented in **two dimensions**, as either the total ion current chromatogram (TICC), base peak chromatogram (BPC), or extracted ion chromatogram (EIC) for a select mass interval (e.g. [99.5, 100.5]). In all these cases, the x axis corresponds to the **scan number** (retention time, in discrete time steps) and the y axis corresponds to **ion current** at the given scan number. Here is a plot of the TICC of real GC-MS data:

![TICC-example](/images/real-ticc.png){: width="800px" }

However, the entire set of data is actually **three-dimensional**; the x axis corresponds to a given **m/z interval**, the y axis corresponds to a given **scan number**, and the z axis corresponds to the **ion current** at a given scan number *and* m/z interval. Here’s a plot of the same data, as a heatmap:

![heatmap-example](/images/real-gcms-heatmap.png){: width="800px" }

Essentially, the TICC corresponds to a **sum** of ion currents (z values) over the entire x axis, the BPC corresponds to choosing (for each y) the **maximum** value of z over the entire x axis, and the EIC for mass $$M_0$$ roughly corresponds to a 2D **cross-section** of the data, along the vertical line $$x = M_0$$. It may be helpful to think of the EIC as the ion current measured across a *single* m/z "channel". The mass spectrum "local" to a particular scan number $$y_0$$, which is displayed in standard GC-MS or LC-MS data processing software when you click on a given scan, likewise corresponds to an orthogonal cross section of the data, along the horizontal line $$y = y_0$$. 

Since each compound corresponds to an “envelope” of molecules, centred at some value of y, you would expect the ion currents (seen as somewhat compressed blobs in the heatmap) observed within different m/z channels to **simultaneously maximise** at some particular scan number, if (fragments of) a **single compound** was responsible for the observed ion currents across those m/z channels. 

Conversely, if you have **multiple** compounds that elute at similar (but not the exact same!) times, then you would observe multiple “clusters” of peak maxima. It is easier to show this with simulated data of two compounds eluting at similar times, like below:

![heatmap-simulated](/images/simulated-combined-heatmap.png){: width="800px" }

Visually, it's clear that the ion current peaks along the m/z don't all "line up" along the x axis. Instead, some of them appear slightly offset from one another. In this case, you can split the ion current peaks into two groups (clusters) which do line up with one another. However, if we visualise the TICC for this simulated data, you can see that it is **not at all obvious** that this peak corresponds to two compounds!

![TICC-simulated](/images/simulated-ticc.png){: width="800px" }

Thus, the core idea of peak deconvolution is to determine rough groups to split the ion current peaks into, in addition to factoring out "stray masses” that maximise at a significantly different time. This allows the “effective TICCs” of both compounds can be **extracted**, as multiple (in this case, two) separate peaks:

![TICC-deconvoluted-simulated](/images/simulated-separated-tic-components.png){: width="800px" }

At a conceptual level, this is how AMDIS, MZMine3, or vendor-specific software perform peak deconvolution. The complication lies in the specific algorithm/s employed by the software to “cluster” the peak maxima, discard “stray masses”, and reconstruct the “effective TICC”. Another complication arises from the fact that in practice, multiple compounds can contribute to the ion current within a **single** m/z channel. This is generally dealt with by selecting "model peaks" for each compound (i.e. peak cluster) detected by the software based on certain peak shape parameters, then **fitting** the model peaks across the remaining channels to resolve the different components *within* m/z channels.
